Auth, access model, API surface, and buildability — researched by an agent, checked by hand.

What was researched, in plain terms

The goal was to study 100 apps and find out how developers log in, whether access is easy or needs approval, what APIs each app offers, whether an AI agent could use it today, and whether the AI's own research was actually correct.

76 of 100 apps got fully researched before the run had to stop — see "Why only 76" below. Of those 76:

84%
self-serve access (64/76)
86%
have some MCP mention (65/76)
66%
use OAuth2 as an auth method
92%
judged "buildable today" (70/76)

The big takeaway: most of these apps have usable APIs and could probably be connected to an AI agent. But there's an important warning — the AI's research wasn't always accurate. That's covered in the verification section below.

How apps authenticate: the most common way is OAuth2 — the user clicks something like "Connect to Slack" and the app hands over permission. The next most common is a plain API key, where a developer gets a secret key and gives it to the app. Basic authentication and simple tokens are also used, but less often. OAuth2 showed up in 50 of the 76 apps, API keys in 41 — many apps support both.

Is access easy? Mostly, yes. 64 of 76 apps are self-serve, meaning a developer can create an account, generate an API key or OAuth app, and start building — no approval needed. Only 12 apps were gated, meaning they need things like admin approval, business verification, or a sales call. Examples: Salesforce, LinkedIn Ads, Meta/Threads, DataForSEO, Amazon Selling Partner, and Datadog.

One warning on the MCP number: "65/76 mention MCP" does NOT mean 65 apps definitely have a working MCP server. It only means the word "MCP" showed up somewhere in the AI's research summary for that app. Treat it as a rough signal, not a confirmed fact.

Why only 76 apps?

This was not because the research system broke. It ran into API usage limits.

First the pipeline ran on Gemini — it hit Gemini's daily request limit. So the team switched to Groq instead. Groq then hit its own daily token limit too. Even after switching to a second API key, the research stopped at 76/100.

The missing 24 apps are: all 10 Finance/Fintech apps, all 10 AI/Research/Media apps, and 4 Productivity apps (ClickUp, Coda, Smartsheet, Harvest). So this report does not represent all 100 apps equally — that's reported plainly here rather than hidden.

How the agent worked

The agent (agent.py) used a two-step process for every app, calling Composio's own search tool:

  • Step 1 — Search. The AI was given an app name and website and one tool, a web search, and told to look for authentication, API details, access requirements, and whether an agent could use the app — preferring the app's own official documentation first. It searched a few times per app before summarizing what it found.
  • Step 2 — Structure the answer. The AI then converted its research into fixed fields: App → Auth → Access → API → Verdict → Evidence → Confidence.
  • Saved after every app. This was useful because if the process crashed or hit a rate limit, it could pick back up instead of starting over from zero.

Where a human is needed: 4 of the 76 completed rows were flagged by the pipeline itself as needing human review (it couldn't find enough to fill in the core fields). Beyond that, the verification below shows the AI's own "confidence" label wasn't a reliable sign of whether an answer was actually correct — so a human still needs to spot-check important results.

Verification: how accurate is it, really

Method: 16 apps were pulled from the completed 76 and checked by hand against the actual developer docs (Zendesk's row didn't have enough info to score and was dropped, leaving 15 scored apps). Each of 5 fields — auth method, self-serve/gated, API surface, buildability verdict, and evidence link — was marked correct or not against the real docs.

60%
auth method correct (9/15)
93%
self-serve/gated correct (14/15)
67%
API surface correct (10/15)
60%
verdict correct (9/15)
53%
evidence link valid (8/15)

Bottom line: 53% (8/15) fully correct on every field at once. The strongest field by far is self-serve-vs-gated (93%) — that's the easiest thing to find in docs and the model gets it right almost every time. The weakest is evidence links (53%): several "correct-sounding" rows cited a URL that either didn't exist, didn't back up the claim, or pointed at an unofficial mirror instead of the real docs.

What broke, with examples

AppWhat went wrong
CloseAgent said no public OAuth2 app / API surface; docs actually show a proper OAuth2 app flow. Verdict marked wrong.
BigCommerceAuth method came back "not available" even though BigCommerce documents OAuth clearly. Verdict marked wrong.
EcwidAuth method returned no data, and the cited evidence URL didn't resolve to anything useful ("no URL").
SquarespaceAPI surface tag was wrong (called it something other than REST) and evidence URL was invalid.
LiveAgent, DataForSEOBoth correctly identified OAuth but the verdict/evidence combo was marked "not fully available" — docs existed but the specific claim wasn't well backed.
ZendeskDropped from scoring entirely — the manual check didn't have enough to compare against.

Correctly caught, for balance: WooCommerce, systeme.io, Telegram, Discord, Shopify, Bright Data, and Vercel/Snowflake all came back fully correct on every field — mostly apps with a single, clearly documented public REST API and one obvious auth method, which is exactly where an LLM-plus-search agent should do well.

Read on the confidence label: the agent's own "High / Medium / Inferred" tag didn't line up cleanly with which rows verification caught as wrong — some of the errors above (BigCommerce, Close) were tagged Medium/High confidence, not Inferred. So confidence, as currently produced, isn't a substitute for spot-checking.

This was a single verification pass, not an iterate-and-remeasure loop — there's no earlier/later accuracy number to report, just the one honest pass above. Given more time, the next step would be a second pass that re-runs only the rows verification flagged as wrong, with a stricter prompt (require the exact doc URL to be fetched and re-checked before the model can claim a fact from it) rather than trusting search-snippet text alone.

Known limitations

  • 24/100 apps not researched (whole Finance/Fintech and AI/Research/Media categories) due to API quota limits — see above.
  • Evidence URLs are agent-reported, not link-checked automatically; verification found 2 of 15 sampled evidence links were invalid or didn't resolve.
  • "MCP mention" in the table is a keyword signal from the agent's summary, not a confirmed working MCP server for every app tagged Yes.
  • Confidence labels (High/Medium/Inferred) are the model's self-assessment and don't reliably predict which rows verification will catch as wrong.
  • Verification covered 15 of 76 completed apps (~20%); the accuracy numbers above are a sample estimate, not a full-dataset audit.
